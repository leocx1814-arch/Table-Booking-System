# การวิเคราะห์ความต้องการเชิงระบบอย่างละเอียด (Detailed Requirements Analysis)

เอกสารฉบับนี้จัดทำขึ้นโดย Senior Full-stack Software Architect, Business Analyst และ Project Manager เพื่อนำเสนอการวิเคราะห์ความต้องการอย่างละเอียดสำหรับ **ระบบจองโต๊ะโรงอาหารในสถานศึกษา (Canteen Table Booking System)** โดยวิเคราะห์ต่อยอดจาก [01-system-overview.md](file:///d:/Table-Booking-System/docs/planning/01-system-overview.md) และปรับปรุงระบบรับเรื่องร้องเรียนเพื่อให้ครอบคลุมตามทิศทางความปลอดภัยและการบริการที่แข็งแกร่ง

---

## 1. วัตถุประสงค์ของระบบ (System Objectives)

1. **เพิ่มประสิทธิภาพในการจัดสรรทรัพยากรโรงอาหาร:** ป้องกันปัญหานักศึกษาและบุคลากรแย่งโต๊ะกันในช่วงเวลาพักกลางวัน (Peak Load)
2. **สร้างช่องทางรับเรื่องร้องเรียนแบบบูรณาการ (Omnichannel Grievance System):** รองรับการยื่นเรื่องร้องเรียนปัญหาในโรงอาหารจากหลายช่องทาง ได้แก่ เว็บแอปพลิเคชัน, โทรศัพท์ติดต่อเจ้าหน้าที่ และการเชื่อมต่อข้อมูลนำเข้าจากระบบร้องเรียนกลางของสถานศึกษา
3. **ส่งเสริมวินัยการใช้งานพื้นที่สาธารณะ:** มีระบบควบคุมพฤติกรรม ตรวจสอบตำแหน่งเช็คอินจริง คุมเวลาใช้งาน และลงโทษผู้ละเมิดกฎอย่างยุติธรรมผ่านกลไก Penalty Points
4. **สนับสนุนการตัดสินใจเชิงบริหาร:** จัดเตรียมแดชบอร์ดแสดงข้อมูลความหนาแน่น สถิติปัญหาร้องเรียน เพื่อช่วยปรับปรุงการจัดผังและบริการของโรงอาหารในระยะยาว

---

## 2. ปัญหาของระบบเดิม (Problems of the Legacy System)

* **ปัญหากดดันจากการกั๊กที่นั่ง (Table Squatting):** ผู้ใช้บางกลุ่มนำสิ่งของส่วนตัว (เช่น กระเป๋า สมุด ขวดน้ำ) มาวางจับจองโต๊ะไว้ล่วงหน้าก่อนจะไปยืนต่อคิวซื้ออาหาร ทำให้โต๊ะไม่มีการใช้งานจริงเป็นเวลานาน แต่ผู้ใช้รายอื่นที่ถือจานอาหารแล้วกลับไม่สามารถนั่งได้
* **ปัญหานั่งแช่เกินเวลา (Overstaying):** ผู้ใช้งานที่รับประทานอาหารเสร็จเรียบร้อยแล้ว แต่นั่งคุยโทรศัพท์ เล่นเกม ทำงานกลุ่มต่อเป็นเวลานาน โดยไม่มีระบบคอยตักเตือนหรือแจ้งเวลาสิ้นสุดสิทธิ์
* **ช่องทางรับเรื่องร้องเรียนไม่มีการรวมศูนย์:** 
  * เมื่อเกิดการโต้เถียงแย่งชิงโต๊ะ หรือพบโต๊ะสกปรก/ชำรุด ผู้ใช้ไม่มีช่องทางแจ้งเรื่องร้องเรียนที่เข้าถึงได้ทันที
  * หากมีการร้องเรียนผ่านโทรศัพท์ไปยังแผนกปกครอง หรือแจ้งปัญหาผ่านแอปพลิเคชันกลางของโรงเรียน ข้อมูลมักตกหล่น ล่าช้า และไม่ได้รับการประสานงานมายังเจ้าหน้าที่โรงอาหารโดยตรง
* **ขาดการบังคับใช้มาตรการทางกฎระเบียบ:** เจ้าหน้าที่โรงอาหารมีจำนวนจำกัด ไม่สามารถเดินตรวจตราและควบคุมพฤติกรรมกั๊กที่นั่งได้ตลอดเวลา และระบบเดิมไม่มีข้อมูลประวัติผู้ใช้ที่ละเมิดกติกาซ้ำซาก

## 3. เป้าหมายของระบบใหม่ (Goals of the New System)

* **จัดคิวโปร่งใสและตรวจสอบได้:** สมาชิกสามารถดูสถานะโต๊ะแบบเรียลไทม์ผ่าน Interactive Seat Map และล็อกการจองได้ด้วยกติกายุติธรรม (1 บัญชีจองได้สูงสุด 1 โต๊ะในเวลาเดียวกัน)
* **กลไกตรวจสอบผู้ใช้งานจริง (Proof of Presence):** บังคับใช้การยืนยันตัวตนแบบ 2 ปัจจัย ได้แก่ การสแกนรหัส QR Code ประจำโต๊ะ ร่วมกับการเช็คตำแหน่งพิกัดผ่านสัญญาณดาวเทียม (GPS Geolocation Check) เพื่อป้องกันการจองและเช็คอินจำลองจากนอกพื้นที่โรงอาหาร
* **ระบบร้องเรียนแบบรวมศูนย์รองรับ Omnichannel:**
  * **ทางเว็บไซต์ (Web App):** ผู้ใช้แจ้งปัญหาผ่านมือถือขณะอยู่ที่โต๊ะได้ทันที
  * **ทางโทรศัพท์ (Phone-in):** เจ้าหน้าที่สามารถกรอกฟอร์มรับเรื่องร้องเรียนที่โทรเข้ามาแจ้งได้รวดเร็ว
  * **นำเข้าจากระบบกลาง (Central API Integration/Import):** รองรับการดึงข้อมูลประเด็นร้องเรียนเกี่ยวกับโรงอาหารจากระบบกลางของสถานศึกษาเพื่อรวมศูนย์ประมวลผล
* **ระบบปรับพฤติกรรมอัตโนมัติ (Automated Deterrents):** ตัดสิทธิ์การจองโดยอัตโนมัติหากไม่มาเช็คอินใน 10 นาที (Auto-Release Status) และหักคะแนนความประพฤติหากกระทำผิดกฎบ่อยครั้ง

## 4. ความต้องการเชิงฟังก์ชัน (Functional Requirements)

ความต้องการเชิงฟังก์ชันถูกแบ่งออกตามกลุ่มผู้มีสิทธิ์ใช้งานระบบ (User Roles) ดังต่อไปนี้:

### 4.1 ระบบสำหรับผู้ใช้งานทั่วไป (นักศึกษา / บุคลากร)
* **FR-USER-01 (Interactive Seat Map):** ผู้ใช้สามารถคลิกเปิดผังโรงอาหารจำลอง แสดงพิกัดโต๊ะแบ่งตามสีของสถานะ (ว่าง, รอเช็คอิน, ใช้งานอยู่, ชำรุด/งดบริการ)
* **FR-USER-02 (Booking):** ผู้ใช้สามารถกดจองโต๊ะว่างผ่านระบบได้ โดยจองได้ทีละ 1 โต๊ะ และมีเวลาจำกัดให้เดินทางไปเช็คอินภายใน 10 นาที
* **FR-USER-03 (Check-in via QR & GPS):** ผู้ใช้สแกน QR Code ที่แปะอยู่บนโต๊ะเพื่อเช็คอิน โดยระบบต้องตรวจสอบว่าตำแหน่ง GPS ของอุปกรณ์ผู้ใช้ตรงกับพิกัดรัศมีพื้นที่โรงอาหารที่กำหนด
* **FR-USER-04 (Check-out/Release):** ผู้ใช้สามารถกดปุ่มเช็คเอาต์ผ่านแอปพลิเคชันเพื่อคืนสถานะโต๊ะว่างเมื่อใช้งานเสร็จสิ้นก่อนหมดเวลา
* **FR-USER-05 (Web Complaint Submission):** ผู้ใช้สามารถส่งข้อร้องเรียนผ่านหน้าเว็บได้ โดยกรอกหมายเลขโต๊ะ เลือกประเภทปัญหา (วางของกั๊ก, นั่งแช่, โต๊ะชำรุด/สกปรก) แนบภาพถ่ายหลักฐาน และพิมพ์ระบุข้อความอธิบายเพิ่มเติม
* **FR-USER-06 (Complaint & Penalty Tracking):** ผู้ใช้สามารถดูรายการเรื่องร้องเรียนที่ตนเองแจ้ง และตรวจสอบประวัติคะแนนความประพฤติ (Penalty Points) รวมถึงวันสิ้นสุดการติด Blacklist ของตนเองได้

### 4.2 ระบบสำหรับเจ้าหน้าที่และผู้ดูแลระบบ (Admin / Canteen Staff / Inspector)
* **FR-ADMIN-01 (Phone-in Complaint Logging):** เจ้าหน้าที่สามารถเปิดฟอร์มเพื่อบันทึกเรื่องร้องเรียนที่โทรศัพท์เข้ามาแจ้ง โดยคีย์รายละเอียดหมายเลขโต๊ะ ประเภทปัญหา ข้อมูลผู้แจ้ง (ถ้ามี) และบันทึกเข้าระบบ
* **FR-ADMIN-02 (Central System Integration/Import):** ระบบต้องรองรับเครื่องมือช่วยอัปโหลดไฟล์นำเข้า (CSV/Excel) หรือมี API Endpoint สำหรับรับข้อมูลการร้องเรียนด้านโรงอาหารจากระบบส่วนกลางของสถานศึกษา
* **FR-ADMIN-03 (Complaint Lifecycle Management):** แอดมินสามารถสืบค้น คัดกรอง มอบหมายเรื่องร้องเรียนให้เจ้าหน้าที่สารวัตรโรงอาหารเข้าตรวจสอบ และเปลี่ยนสถานะเรื่องร้องเรียน (รอดำเนินการ, กำลังสืบสวน, ดำเนินการเสร็จสิ้น, ปฏิเสธคำร้อง)
* **FR-ADMIN-04 (Penalty & Blacklist Administration):** แอดมินสามารถลดยกเลิกคะแนน ตรวจสอบประวัติพฤติกรรม และทำการปลดล็อคการระงับสิทธิ์ใช้งานบัญชีนักเรียน (Blacklist Override) แบบแมนนวลได้
* **FR-ADMIN-05 (Interactive Live Monitor):** แผง Dashboard แสดงสัดส่วนโต๊ะว่าง/ใช้งาน (Live Occupancy Rate), คิวข้อร้องเรียนเร่งด่วนเรียงตามเวลา, และระบบแจ้งเตือนเมื่อเกิดความขัดแย้งในการใช้โต๊ะ
* **FR-ADMIN-06 (Seat Layout & QR Code Config):** แอดมินสามารถเพิ่ม ลด แก้ไข พิกัดโต๊ะในโรงอาหาร และกดดาวน์โหลดรูปภาพ QR Code ประจำโต๊ะแต่ละตัวเพื่อนำไปติดพิมพ์ลงกระดาษจริง

### 4.3 ระบบเบื้องหลังการทำงานและบริการอัตโนมัติ (Backend Services & Automation)
* **FR-SYS-01 (Pessimistic Row Lock):** ป้องกัน Race Condition เมื่อมีทราฟฟิกเข้ามาจองโต๊ะตัวเดียวกันพร้อมกัน โดยใช้ Transaction Lock ที่แถวของโต๊ะนั้น ๆ
* **FR-SYS-02 (Auto-Release Cron Service):** ระบบรันตรวจสอบฐานข้อมูลทุก ๆ 1 นาที เพื่อเปลี่ยนสถานะการจองที่เกินเวลาเช็คอิน (10 นาที) ให้เป็นสถานะ Expired และปลดโต๊ะคืนเป็น Available
* **FR-SYS-03 (Overstay Auto Check-out Service):** ระบบปลดสิทธิ์ครองโต๊ะอัตโนมัติหลังหมดโควตา 30-45 นาทีนับจากการเช็คอินจริง
* **FR-SYS-04 (Notification Service):** ส่งข้อความแจ้งเตือนแจ้งผลการตัดสินเรื่องร้องเรียน, หักคะแนนความประพฤติ, และแจ้งเตือนเตือนล่วงหน้า 5 นาทีก่อนหมดสิทธิ์นั่งโต๊ะ

## 5. ความต้องการที่ไม่ใช่ฟังก์ชัน (Non-functional Requirements)

* **NFR-PERF-01 (Peak Load Performance):** ระบบ backend และฐานข้อมูล MySQL ต้องประมวลผลคำขอจองและเช็คอินได้น้อยกว่า 1.5 วินาที แม้ในช่วงเวลาที่มีคนใช้งานพร้อมกันสูง (Peak Load) ถึง 1,000 Concurrent Requests
* **NFR-PERF-02 (Map Real-time Synced):** สถานะสีของโต๊ะบน Interactive Seat Map ฝั่งผู้ใช้งานทั้งหมดต้องอัปเดตตรงกันภายใน 2 วินาทีหลังมีการเช็คอินหรือเช็คเอาต์ ผ่านเทคโนโลยี Server-Sent Events (SSE) หรือ WebSockets
* **NFR-USAB-01 (Mobile-Responsive Design):** หน้าจอหน้าเว็บแอปพลิเคชันต้องเป็นแบบ Responsive ที่สวยงามและพกพาสะดวกสำหรับสมาร์ตโฟน (Mobile-First) เนื่องจากนักศึกษาเดินใช้งานขณะมือถือถือจานอาหารเป็นหลัก
* **NFR-SEC-01 (Password Encryption & Protection):** รหัสผ่านของผู้ใช้ต้องถูกเข้ารหัสลับผ่านกระบวนการ Hashing แบบ One-way ด้วยอัลกอริทึม bcrypt ก่อนบันทึกลงฐานข้อมูล
* **NFR-SEC-02 (Geolocation Privacy):** พิกัดละติจูดและลองจิจูดจริงของผู้ใช้ที่ส่งมาเช็คอินจะถูกประมวลผลเฉพาะตอนทำธุรกรรมเพื่อเปรียบเทียบขอบเขตรัศมีโรงอาหารเท่านั้น และจะไม่มีการเก็บบันทึกประวัติตำแหน่งผู้ใช้ลงฐานข้อมูลถาวรเพื่อพิทักษ์ข้อมูลส่วนบุคคล
* **NFR-RELI-01 (ACID Database Properties):** การจองและการเปลี่ยนสถานะโต๊ะต้องรักษาความถูกต้องสมบูรณ์ของฐานข้อมูล (Database Integrity) หากธุรกรรมตัวใดพังกลางทาง ระบบต้อง Rollback กลับค่าเริ่มต้นทันทีเพื่อไม่ให้มีโต๊ะติดค้างในระบบ

## 6. ข้อมูลที่ระบบต้องจัดเก็บ (Data Storage Requirements)

ระบบฐานข้อมูล MySQL 8 จะจัดเก็บข้อมูลตารางหลักดังต่อไปนี้ (ยังไม่ลงลึกถึง Data Type และ FK Constraints):

| กลุ่มข้อมูล | รายการข้อมูลหลักที่ต้องการจัดเก็บ |
| :--- | :--- |
| **ข้อมูลผู้ใช้ (Users)** | User_ID, Username, Password (Hashed), Email, Firstname, Lastname, Student_ID (หรือ Employee_ID), Role (Student, Admin, Inspector), Penalty_Points (เริ่มต้น 100), Blacklist_Status, Blacklist_Until_Date |
| **ข้อมูลโต๊ะ (Tables)** | Table_ID, Table_Number, Zone_Name, Layout_X, Layout_Y, Status (Available, Pending_Checkin, Occupied, Maintenance), QR_Verification_Code, Created_At |
| **ข้อมูลการจอง (Bookings)** | Booking_ID, User_ID, Table_ID, Booked_At, Expired_At, Checked_In_At, Checked_Out_At, Expected_End_At, Booking_Status (Pending, Active, Completed, Expired, Cancelled) |
| **ข้อมูลข้อร้องเรียน (Complaints)**| Complaint_ID, Source (Web, Phone, Central_API), Reporter_User_ID (Null หากไม่ระบุตัวตน), Receiver_Admin_ID (กรณีรับเรื่องทางโทรศัพท์), Table_ID, Complaint_Type (Hogging, Overstay, Damage, Cleanliness), Evidence_Image_URL, Complaint_Description, Status (Pending, Investigating, Resolved, Rejected), Admin_Remarks, Created_At, Resolved_At |
| **ข้อมูลบันทึกคะแนน (Penalty_Logs)**| Log_ID, User_ID, Booking_ID (หรือ Complaint_ID ที่เชื่อมโยง), Deducted_Points, Deducted_At, Reason_Description |
| **ข้อมูลการตั้งค่า (System_Settings)**| Setting_ID, Key_Name (เช่น Max_Session_Min, Checkin_Grace_Min, Canteen_Latitude, Canteen_Longitude, Canteen_Radius_Meters), Key_Value |

## 7. ข้อมูลที่ระบบต้องแสดงผล (Information Output Requirements)

### 7.1 หน้าจอแสดงผลสำหรับผู้ใช้งานทั่วไป (Student/Staff App UI)
* **แผนผังโรงอาหารจำลอง (Interactive Map Visualization):** ผังที่นั่งแบ่งสถานะสีเพื่อช่วยให้นักเรียนตัดสินใจได้รวดเร็ว
* **ป้ายแสดงผลข้อมูลจองปัจจุบัน (Active Reservation Card):** 
  * แสดงหมายเลขโต๊ะที่ตนเองจองค้างอยู่
  * แสดงตัวเลขนับถอยหลังการเข้าเช็คอิน (Countdown Timer) เป็นนาทีและวินาที
  * แสดงตัวเลขนับถอยหลังเวลาการใช้โต๊ะอาหารที่เหลืออยู่ (Session Timer)
* **แดชบอร์ดความรู้พฤติกรรมผู้ใช้ (My Profile & Stats):** ประวัติรายการร้องเรียนของตนเอง คะแนนความประพฤติ และสถิติความรวดเร็วในการเช็คเอาต์เพื่อสร้างวินัยเชิงบวก

### 7.2 แผงรายงานสำหรับผู้ดูแลระบบและสารวัตรโรงอาหาร (Admin Control Dashboard)
* **สถิติเรียลไทม์ (Live Occupancy Rate):** ร้อยละการครองโต๊ะในปัจจุบัน โต๊ะที่ถูกใช้บ่อยที่สุด และอัตราความหนาแน่นรายชั่วโมง
* **รายการคิวเรื่องร้องเรียนเร่งด่วน (Urgent Complaint Queue):** แสดงตารางรายการข้อร้องเรียนล่าสุดที่ยังไม่ได้ดำเนินการ มีการแนบรูปถ่ายหลักฐาน พิกัดโต๊ะ เพื่ออำนวยความสะดวกในการกดดู
* **บัญชีข้อมูลผู้กระทำผิด (Violation Management):** รายการชื่อผู้ใช้ที่ติด Blacklist และยอดการหักคะแนนความประพฤติในสัปดาห์นี้
* **รายงานเชิงสถิติ (Analytical Reports):** สถิติจำนวนครั้งการยกเลิกจองอัตโนมัติ (No-Show) ข้อมูลประเภทปัญหาร้องเรียนที่พบบ่อย (เช่น วางของกั๊ก 60%, นั่งแช่ 30%) เพื่อประกอบการตัดสินใจของสถานศึกษา

## 8. เงื่อนไขและกฎทางธุรกิจของระบบ (Business Rules)

1. **สิทธิ์ผูกขาดต่อบัญชีใช้งาน (Single Booking Lock):**
   * ผู้ใช้ 1 คนสามารถมีธุรกรรมการจองที่อยู่ในสถานะ `Pending_Checkin` หรือ `Occupied` ได้เพียง **1 รายการเท่านั้น** ในช่วงเวลานั้น ๆ ห้ามจองซ้ำซ้อน
2. **ขอบเขตระยะเวลาและพื้นที่เช็คอิน:**
   * ผู้ใช้ต้องทำรายการเช็คอินผ่านการสแกน QR Code ภายใน **10 นาที** หลังจากการกดจอง มิฉะนั้นการจองจะหมดอายุทันที
   * ระยะพิกัด GPS ของสมาร์ตโฟนตอนเช็คอิน ต้องอยู่ห่างจากจุดศูนย์กลางพิกัดโรงอาหารไม่เกินรัศมี **50 เมตร** (Canteen_Radius_Meters)
3. **ระยะเวลาครองพื้นที่โต๊ะ:**
   * สิทธิ์การใช้งานโต๊ะอาหารสูงสุดกำหนดไว้ที่ **30 นาทีต่อการจอง 1 ครั้ง** หากครบกำหนดเวลาโดยผู้ใช้ไม่เช็คเอาต์ ระบบจะตัดสิทธิ์และตั้งค่าโต๊ะกลับเป็น "ว่าง" เพื่อไม่ให้ขัดขวางคิวถัดไป
4. **เกณฑ์การคิดคะแนนความประพฤติและการโดน Blacklist:**
   * คะแนนความประพฤติเริ่มต้น = 100 คะแนน
   * จองโต๊ะแล้วปล่อยสิทธิ์จนหมดเวลาเช็คอิน (No-Show Expired): หัก 5 คะแนน
   * นั่งแช่เกินเวลา / วางสิ่งของกั๊กโต๊ะ และถูกแอดมินหรือสารวัตรยืนยันจากเรื่องร้องเรียนว่าผิดจริง: หัก 20 คะแนน
   * หากคะแนนประพฤติ **ต่ำกว่า 50 คะแนน**: ผู้ใช้รายนั้นจะถูกปรับเข้าสู่สถานะ **Blacklist** โดยระบบจะตัดสิทธิ์ไม่ให้จองโต๊ะล่วงหน้าผ่านแอปพลิเคชันเป็นเวลา 7 วันเต็ม (แต่ยังสามารถใช้งานแบบเดินเข้าปกติหากมีโต๊ะว่างและไม่มีผู้จอง)
5. **นโยบายการเคลมและยื่นเรื่องร้องเรียน:**
   * เพื่อป้องกันการกลั่นแกล้งกัน ข้อร้องเรียนเกือบทั้งหมดต้องการรูปถ่ายพยานยืนยัน และสารวัตรโรงอาหารหรือแอดมินจำต้องกดอนุมัติ "ยืนยันการทำผิดกฎ" (Verify Violation) ก่อนคะแนนความประพฤติของบุคคลเป้าหมายจะถูกหักจริง

## 9. ข้อจำกัดและข้อควรระวัง (System Constraints & Risks)

> [!CAUTION]
> **1. ปัญหาความแม่นยำของพิกัดดาวเทียม (GPS Inaccuracy in Buildings):**
> อาคารโรงอาหารส่วนใหญ่มักมีสิ่งกีดขวาง สัญญาณโทรศัพท์และสัญญาณ GPS อาจเกิดการคลาดเคลื่อน (GPS Drift) ทำให้ระบบเช็คอินบอกว่านักศึกษาอยู่ไกลเกินขอบเขต 50 เมตร
> * *ข้อเสนอแนะ:* ต้องตั้งค่ารัศมีขอบเขตให้มีความปลอดภัยและยืดหยุ่น (เช่น 50-80 เมตร) หรือตั้ง Wi-Fi SSID ของโรงอาหารเป็นตัวช่วยยืนยันตำแหน่งแทน GPS
> 
> **2. การแอบบันทึกรูป QR Code (QR Code Spoofing):**
> นักเรียนอาจแอบถ่ายภาพป้าย QR Code ที่โต๊ะและส่งต่อไปให้เพื่อนที่อยู่นอกโรงอาหารเพื่อกดสแกนเช็คอินหลอก ๆ
> * *ข้อเสนอแนะ:* ระบบตรวจสอบพิกัด GPS จะช่วยลดความเสี่ยงนี้ได้ 1 ชั้น หรือในอนาคตจำเป็นต้องเสริมรหัส PIN เช็คอินที่มีการเปลี่ยนค่าอัตโนมัติ
> 
> **3. พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล (PDPA Constraints):**
> การอัปโหลดรูปภาพหลักฐานข้อร้องเรียนอาจมีรูปใบหน้าของนักศึกษาคนอื่นหรือบุคคลภายนอกติดเข้ามา ซึ่งมีความเสี่ยงในทางกฎหมายข้อมูลส่วนบุคคล
> * *ข้อเสนอแนะ:* หน้าจอแนบรูปต้องระบุข้อตกลงและเงื่อนไข (Consent) ชัดเจนว่ารูปภาพนี้จะใช้เพื่อวัตถุประสงค์ในการตรวจสอบภายในโรงอาหารเท่านั้น และระบบควรมีกำหนดการลบไฟล์รูปภาพการร้องเรียนที่เสร็จสิ้นแล้วออกจากระบบภายใน 30 วัน
> 
> **4. ข้อจำกัดของพื้นที่จัดเก็บข้อมูลบนระบบ Railway (Ephemeral Storage Limit):**
> ไฟล์รูปภาพพยานหลักฐานเรื่องร้องเรียนที่ผู้ใช้อัปโหลดเข้ามา หากจัดเก็บลงในพื้นที่โฟลเดอร์ของ Docker Container ตรง ๆ จะเกิดการสูญหายเมื่อคอนเทนเนอร์ทำระบบ Re-deploy ใหม่บนคลาวด์
> * *ข้อเสนอแนะ:* ต้องต่อ API กับคลาวด์พื้นที่จัดเก็บภายนอก เช่น Cloudflare R2 หรือ AWS S3 หรือใช้วิธีเก็บรูปขนาดเล็กมากในฐานข้อมูล MySQL ตรง ๆ ในรูปแบบ Base64 (สำหรับการรันเพื่อทดสอบโปรเจกต์เท่านั้น)

## 10. คำถามสำหรับสอบถามผู้ใช้งานและผู้มีส่วนได้ส่วนเสียเพิ่มเติม (Clarifying Questions for Stakeholders)

เพื่อปรับแต่งเอกสารการออกแบบฐานข้อมูล (Database Schema) ในขั้นตอนถัดไปให้ดียิ่งขึ้น AI Technical Lead ขอเสนอประเด็นคำถามเพิ่มเติมเพื่อหารือกับผู้ใช้งานจริง:

1. **ประเด็นระบบล็อกอินผู้ใช้งาน (SSO Integration):**
   * *คำถาม:* ทางโรงเรียน/มหาวิทยาลัยต้องการให้เชื่อมโยงระบบการยืนยันตัวตนกับระบบ SSO ส่วนกลาง (เช่น Google Workplace, Active Directory, หรือ OAuth ของโรงเรียน) หรือไม่ หรือต้องการให้ทีมงานสร้างโมดูลการลงทะเบียน สมัครสมาชิก และบันทึกรหัสผ่านใน MySQL แยกเฉพาะของระบบนี้เลย?
2. **ประเด็นช่องทางการดึงข้อมูลร้องเรียนของระบบกลาง (Central API Specification):**
   * *คำถาม:* ระบบร้องเรียนกลางของสถานศึกษาที่ต้องการให้นำข้อมูลเข้ามารวมศูนย์นั้น มี API Endpoint ที่เราสามารถเข้าดึงข้อมูลแบบเรียลไทม์ได้โดยตรง หรือทางสถานศึกษาจะใช้วิธีส่งออกไฟล์เป็นไฟล์รายงาน Excel รายวันเพื่อให้อัปโหลดเข้าฐานข้อมูลแบบแมนนวล?
3. **ประเด็นสิทธิ์การบริหารจัดการของร้านค้าโรงอาหาร (Shop Owners Role):**
   * *คำถาม:* มีความจำเป็นต้องสร้างบทบาทการใช้งานสำหรับ "เจ้าของร้านค้าในโรงอาหาร" หรือไม่ เพื่อให้ร้านค้าสามารถกดดูความหนาแน่นของผู้ใช้ผ่านหน้าเว็บ ตรวจดูเรื่องร้องเรียนรอบร้านตัวเอง หรือช่วยกดปลดสถานะเคลียร์โต๊ะหน้าร้านของตนเองเมื่อพบว่าว่าง?
4. **ประเด็นกลไกการล้างคะแนนความประพฤติ (Score Recovery System):**
   * *คำถาม:* การคืนคะแนนความประพฤติควรมีเงื่อนไขอย่างไร เช่น เมื่อสแกนจองโต๊ะและมีพฤติกรรมเช็คเอาต์ตรงเวลาครบ 5 ครั้ง จะได้รับคะแนนประพฤติคืน 10 คะแนน หรือให้ระบบล้างสิทธิ์คะแนนรีเซ็ตกลับไปเป็น 100 คะแนนเต็มในทุกช่วงต้นภาคการศึกษาใหม่?
